# 可信问数闭环 设计文档

> 子项目范围：Data Agent 首个子项目。上游范围基线见 `chanp.md`。
> 本文档中的 M-xx / S-xx / D-xx / J-x 编号均指向 `chanp.md` 的对应条目。

## 1. 目标与非目标

### 目标

在单个数据集上跑通一条可信的问数链路，做到 `chanp.md` 定义的三件事：数出得准、口径讲得清、错了查得到。

具体覆盖：语义层最小集（M-01/M-02/M-03/M-04/M-05/M-07）、结构化意图（M-17）、澄清（M-18）、结构化多轮上下文（M-19）、Verified Query（M-20）、分阶段 Pipeline（M-09）、AST 白名单（M-10）、行级权限（M-11）、列权限与脱敏（M-12）、成本护栏（M-13）、结果校验（M-15）、引证（M-16）、工作台（M-39）、反馈归因（M-38 的采集部分）、Trace（M-34）。

### 非目标（本轮明确不做）

| 项 | 理由 |
|---|---|
| 多表 Join 与 Join Planner（M-06） | 本轮限定单数据集，宽表或预定义视图。Join 的基数与重复计数问题留给下一轮专门处理 |
| AI 辅助语义初始化（M-08） | 命中 J5 是为解决几百张表的交付成本，本轮只有一个样本数据集，人工配置更快更准 |
| 执行失败 LLM 自愈（M-14） | 见 5.4。自愈的价值绑定在「LLM 写 SQL」的架构上，本轮架构下不成立 |
| 图表规划器（M-25） | 本轮成果区只有结果表与导出 |
| 报告（M-26） | 依赖图表与深度分析 |
| 双模式 / 深度分析（M-21/M-22/M-23） | 本轮只做智能问数单链路，输入框无模式选择器 |
| 完整评测中心（M-35/M-36/M-37） | 端到端问题集按 Golden Set 格式编写，下一轮直接升级 |
| Python 沙箱（M-24） | 无 SQL 表达不了的需求进入本轮范围 |
| 报告/图表之外的其余 MUST | 见 `chanp.md`，按后续子项目推进 |

多模态数据理解（D-03）、业务动作回写（D-01）在范围基线中已明确排除，本轮及后续均不做。历史代码中的 `nl2multimodal.py`、`media_processing.py`、`annotation_*` 与该结论冲突，不纳入新实现。

## 2. 核心设计决策

### 决策：LLM 不生成 SQL

LLM 在整条链路中只有一个介入点——把自然语言转成结构化意图。SQL 由确定性编译器从「意图 + 语义模型 + 指标定义」生成。

考虑过的替代方案：

- **LLM 生成 SQL + 强校验**：覆盖面更广，但 AST 校验只能证明 SQL 安全、可执行、结果不离谱，证明不了它算的是业务要的口径。毛利率被写成另一种算法，校验完全看不出来——这正是 J1 静默错误。且引证需反解析 SQL 才能拼出，口径行不可靠。
- **Verified Query 为主**：冷启动时无沉淀，兜底路径才是真正的系统。它是前置缓存层，不是独立架构。

选择编译器的理由：

1. 同一份意图必然编译出同一条 SQL，满足 M-04「同一个问题两次结果不同企业无法接受」。
2. 时间窗口函数由内置模板生成，满足 M-05「不由 LLM 生成」。
3. 引证是免费的——口径、时间、过滤条件本就是编译输入，无需反向推断。
4. 错误可归因：数字错了，要么意图抽错，要么指标配错，两者都能在 Trace 里定位。
5. 从意图往后全是确定性纯函数，可密集单测。

代价：表达力受限于编译器支持的意图形状，模板外的问题只能拒答或转澄清。接受这个代价——`chanp.md` 的判断是「一个会编数的 Agent 比一个会拒答的 Agent 危险得多」。

M-10 的 AST 白名单仍然实现，作为编译器输出的最后一道兜底闸门，而非给 LLM 的护栏。

## 3. 架构

### 3.1 部署单元

按 S-11 的 7 个部署单元，本轮启用 3 个：

| 服务 | 职责 |
|---|---|
| `api-gateway` | 认证、路由、请求校验 |
| `semantic-service` | 数据集语义、字段语义、枚举值字典、指标定义、语义体检 |
| `query-service` | 意图识别、SQL 编译、安全改写、护栏、执行、结果校验、Trace 写入 |

`platform-service` 本轮只取最简用户/角色与 Trace 只读展示，评测、调度、审计不启用。前端为单个 Vue3 应用。

对 `chanp.md` 的一处偏离：范围基线把 Trace 归入 `platform-service`，本轮由 `query-service` 直接写 Trace 表、platform 侧只读展示，省掉链路上的跨服务调用。Trace 是本轮的调试主力，写入路径越短越好。

### 3.2 数据流

```text
提问
 │
 ├─1 Verified Query 召回 ──命中──► 取固定 SQL ──────────────┐
 │                                                          │
 ├─2 意图识别（LLM 唯一介入点）                              │
 │    输出：intent/metric/time/dimension/filter/comparison   │
 │          + 每字段置信度                                   │
 │                                                          │
 ├─3 语义解析与澄清                                          │
 │    值别名映射（华东→EC）、指标解析、时间口径解析          │
 │    置信度低或有歧义 ──► 澄清卡片 ──► 回到 2               │
 │                                                          │
 ├─4 SQL 编译（无 LLM 参与）                                 │
 │    意图 + 语义模型 + 指标定义 → SQL AST                   │
 │    时间对比走内置模板，聚合函数取字段的"允许聚合"          │
 │                                                          │
 ├─5 安全改写与护栏                              ◄───────────┘
 │    RLS 注入 WHERE、敏感列脱敏、强制 LIMIT
 │    AST 白名单终检、EXPLAIN 成本预估
 │
 ├─6 执行与结果校验
 │    空结果 / 全 NULL / 除零 / 量级突变 → 不直接作答
 │
 └─7 作答
      数字 + 结论 + 引证块（口径/时间/过滤/更新时间）+ 可下钻入口
```

每阶段的输入输出落 Trace，可单独重放（M-09）。

**第 1 步与第 5 步的交汇是有意设计**：Verified Query 的固定 SQL 也必须过安全改写。否则一条沉淀下来的 SQL 会绕过 RLS，成为越权通道。

### 3.3 核心契约：意图 Schema

M-17 定义它为系统的核心契约。它同时是：LLM 的唯一输出、编译器的唯一输入、澄清的判断依据、Trace 的重放单元、评测集的比对对象。**它的定义优先于其他一切实现**。

字段：`intent`（查询类型）、`metric`（指标引用）、`time`（时间范围与粒度）、`dimension`（分组维度）、`filter`（过滤条件）、`comparison`（对比方式），每个字段附带置信度。

## 4. 语义模型与指标

编译器的输入，本轮唯一需要人工配置的部分。

### 4.1 数据集（M-01）

绑定一张物理表或视图。属性：业务名、别名、描述、粒度、适用场景、**禁用场景**。

禁用场景本轮即做——`chanp.md` 称它是唯一能阻止 Agent 拿订单表算财务确认收入的手段。

### 4.2 字段（M-02 子集）

取 M-02 清单中编译器实际会用到的属性。M-02 完整清单里的「所属业务对象」「值别名」「值黑名单」「默认召回」「值召回」「PII 级别」本轮在数据模型中保留字段但不做配置 UI、编译器也不读取——它们服务于多表召回与脱敏分级，属于下一轮范围。

本轮实际生效的属性：

```text
物理名 / 业务名 / 同义词 / 语义类型（金额·数量·比率·日期·ID·枚举·文本）
单位 / 显示格式 / 默认聚合 / 允许聚合
是否可筛选 / 是否可分组 / 是否可查询
敏感级别（用于列权限与脱敏）
```

**「允许聚合」是编译器的硬约束，不是提示**。字段未标 Sum，编译器不产出 SUM。这从机制上挡住对库存余额、客户等级求和这类业务方几乎发现不了的错误。

### 4.3 枚举值字典（M-03）

值 → 别名 → 描述。走独立索引查询，不塞进 Prompt。用户说「华东」，编译器查字典得到 `EC`；映射失败转澄清，不查空。

### 4.4 指标（M-04）

本轮支持四类：

| 类型 | 说明 |
|---|---|
| 原子 | 直接聚合，如 `SUM(amount)` |
| 派生 | 原子 + 固定限定，如新客销售额 |
| 复合 | 指标间运算，如毛利率 |
| 比率 | 标注 `Recalculate`，禁止对比率求和 |

半可加与累计指标本轮不做，但聚合行为字段先留在模型里，避免后续改结构。

每个指标带版本号，引证中显示（如 `sales_revenue v3`）。

**时间口径显式声明**：指标必须指定按哪个日期字段计算（订单创建日 vs 完成日）。这是同一指标出现两个数字的常见原因。

### 4.5 时间计算（M-05）

同比、环比、YoY、MoM、YTD、MTD 由编译器内置模板生成。LLM 只负责识别「用户要的是环比」，不生成窗口函数。

### 4.6 语义体检（M-07）

发布前检查：字段无业务名、指标无口径、枚举无字典、指标引用已删字段。不通过不允许被问答使用——`chanp.md` 称其为质量的第一道闸门。

## 5. 错误处理与失败路径

原则：**任何一步不确定，走澄清或拒答，绝不猜一个数字。**

### 5.1 意图阶段

LLM 返回每字段置信度。指标、时间、维度任一低于阈值转澄清，不带着低置信度往下走。识别不出对应指标时直接拒答并说明原因，不退化成「找个相近字段凑一个」。

### 5.2 澄清（M-18）

覆盖五类歧义：指标歧义（「销售额」对应多个指标定义）、时间歧义（「最近」是 7 天还是本月）、维度歧义、实体歧义（值映射不上）、数据集歧义。

置信度阈值与最大澄清轮数为全局配置（本轮不做按数据集或按 Agent 分别配置）。超过轮数用默认假设作答，但**默认假设必须写在答案里**——不说明的默认假设等于静默错误。

### 5.3 编译阶段

这里的失败是配置问题而非运行时问题：字段不允许该聚合、指标引用不存在的字段、维度字段标了不可分组。

这类错误产出**面向管理员的诊断信息**（指明哪个指标、哪个字段），而不是给终端用户的「查询失败」。

### 5.4 执行失败

本轮自愈范围比 M-14 窄，且这是有意收窄。

SQL 由编译器生成，M-14 要修的「字段名不存在」在本架构下几乎不会发生；一旦发生，说明语义模型与物理表不一致，LLM 重试也没用。

本轮只做：超时与连接失败重试 2 次。其余错误直接归类上报并入 Trace，不做 LLM 改写重试。

### 5.5 结果校验（M-15）

检查空结果、全 NULL、除零、行数异常、量级突变。检出后不直接作答：

- 空结果需区分「真的没有数据」与「筛选条件把数据全滤掉」，后者转澄清
- 量级突变则作答，但显式提示异常

### 5.6 权限失败

无权限的问题必须拒答**且不泄漏元数据**（`chanp.md` 将其列为评测集最容易漏的四类之一）。

表现为「你没有该数据的访问权限」，不能是「表 finance_revenue 需要权限」——后者泄漏了该表存在这一事实。

### 5.7 Trace（M-34）

每阶段记录：输入、输出、模型、Token、耗时、召回内容、编译出的 SQL、错误。

要求是产品化的可查页面，不是日志文件。支持从任一阶段的意图快照重放。

## 6. 前端工作台

三分栏工作区（M-39），不是单纯的问答框：

```text
┌──────────────┬────────────────────────────────┬──────────────────┐
│ 会话列表      │  对话区                         │  证据/成果区      │
│              │                                │                  │
│ 今天          │  ┌──────────────────────────┐  │  当前查询条件     │
│ · 华东销售     │  │ 华东本月销售额 4,235 万   │  │  ┌────────────┐  │
│ · 客单价下降   │  │ 环比 +12.4%              │  │  │指标 销售额▾ │  │
│              │  │                          │  │  │时间 本月  ▾ │  │
│ 昨天          │  │ 主要增长：江苏 +18.2%     │  │  │维度 省份  ▾ │  │
│ · ...         │  │          浙江 +15.6%     │  │  │过滤 华东  ▾ │  │
│              │  │                          │  │  └────────────┘  │
│              │  │ ── 引证 ──────────────    │  │   ↑ 可直接改后重跑│
│              │  │ 口径 sales_revenue v3    │  │                  │
│              │  │ 时间 08-01 ~ 08-12       │  │  ▸ 查看数据       │
│              │  │      （按订单完成日）     │  │  ▸ 查看 SQL      │
│              │  │ 过滤 region IN ('华东')  │  │  ▸ 查看 Trace    │
│              │  │      ← 数据权限自动附加   │  │                  │
│              │  │ 更新 08-12 09:00         │  │  本轮成果         │
│              │  │                          │  │  · 结果表 ↓      │
│              │  │  👍 👎                   │  │                  │
│              │  └──────────────────────────┘  │                  │
│              │  ┌──────────────────────────┐  │                  │
│              │  │ 输入框                    │  │                  │
│              │  └──────────────────────────┘  │                  │
└──────────────┴────────────────────────────────┴──────────────────┘
```

不能省的细节：

**右栏查询条件面板是 M-19 的落地**。多轮上下文维护 metric/time/dimension/filter 这组结构化状态，不是聊天记录堆叠。「那华南呢」只改 filter 一个槽位，其余保持。该状态必须可见且可编辑——用户直接改下拉框重跑，比再问一句更准更快。

**引证块默认展开，不折叠**。企业用户不会信一个说不出口径的数字。「← 数据权限自动附加」这行必须显式出现，否则用户会拿权限内的部分数据下全局结论。

**澄清以卡片形式出现在对话流**，带可点选项（「你指的是哪个销售额：含税订单金额 / 财务确认收入」），不让用户重新打字。

**点踩弹归因分类**（M-38）：指标错、时间错、SQL 错、计算错、结论错。这是后续评测集最真实的数据来源。

本轮输入框无模式选择器（双模式不做），成果区只有结果表与导出，左栏会话列表保留但不做跨会话引用。

### 6.1 配置侧页面

数据集语义、字段语义、枚举字典、指标定义、语义体检、Verified Query、用户与行列权限策略、Trace 查询。

界面朴素优先——使用者是管理员，不是业务方。

### 6.2 组件边界

历史代码的 `QueryPage.vue` 达 3308 行，是把问答、配置、结果全塞进一个文件的结果。本轮按上述分栏拆分为独立组件，每个组件只负责一件事。

## 7. 数据底座

PostgreSQL + 本地样本数据集（订单/销售场景）。

方言层本轮只适配 PostgreSQL（S-02 首发适配 2~3 种，本轮取 1 种）。成本护栏的 EXPLAIN 扫描量预估绑定 PostgreSQL 实现。

选择理由：可重复、可写集成测试、EXPLAIN 真实可用；pgvector 兼顾后续枚举值召回索引（D-05 已定为直接用成熟组件）。

## 8. 测试策略

本架构最大的好处是可测——LLM 不写 SQL，意味着从意图往后全是确定性纯函数。

| 层次 | 内容 |
|---|---|
| **编译器（重点）** | 给定意图 + 语义模型，断言编译出的 SQL 等价。无需 LLM、无需数据库，纯单测。覆盖各类指标、时间模板（同比/环比/YTD/MTD）、允许聚合的拒绝路径、比率指标禁止求和。全项目最密的一层 |
| **安全（必须 100% 通过）** | RLS 是否在所有路径注入（含 Verified Query 路径）、无权列是否在召回阶段即不可见、脱敏是否生效、DDL/DML 是否被 AST 拦截、越权拒答是否不泄漏表名 |
| **意图识别** | 跑真实 LLM，固定问题集断言意图结构。输出有波动，断言槽位正确性而非字面相等 |
| **端到端** | PostgreSQL 样本库 + 已知期望结果的问题集。覆盖简单问数、同比环比、TopN、多维、模糊问题（应触发澄清）、无权限问题（应拒答）、超范围问题（应拒答不能编）。后三类是信任度的关键 |

安全项 100% 通过对齐 `chanp.md` 的发布门禁要求。

端到端问题集按 Golden Set 格式编写，下一轮可直接升级为评测集，无需重写。
